# IEEE-CIS Fraud Detection

An end-to-end machine learning pipeline for fraud detection using temporal feature engineering, historical behavioral features, Vesta feature compression, feature optimization, hyperparameter tuning, and an ensemble of XGBoost, LightGBM, and CatBoost models.

## Overview

This project was developed for the **IEEE-CIS Fraud Detection** Kaggle competition.

The objective was to predict whether an online transaction was fraudulent using transaction-level and identity-level information.

The final pipeline focuses on:

* Point-in-time historical feature engineering
* Proxy user identification
* Transaction velocity and behavioral features
* Sparse Vesta feature compression using PCA
* Feature optimization and pruning
* Chronological validation
* Optuna-based hyperparameter optimization
* XGBoost, LightGBM, and CatBoost models
* Out-of-fold predictions
* Weighted probability blending
* Reproducible train/test feature transformations

The final ensemble achieved:

| Metric                   |     ROC-AUC |
| ------------------------ | ----------: |
| Public leaderboard       |  **0.9402** |
| Private leaderboard      |  **0.9170** |
| Optimized OOT validation | **0.94297** |

# Feature Engineering

## Identity Features

Identity information is processed separately from transaction data.

The identity feature pipeline incorporates information relating to:

* IP information
* Device information
* Identity-related attributes
* Card and address information

These features are then combined with transaction-level information during dataset construction.

---

## Proxy User Identification

A proxy `user_id` is constructed from a combination of:

```text
card1
card2
card3
addr1
D1
```

The purpose is to approximate recurring users across transactions and allow historical behavioral features to be calculated.

This is not intended to represent a perfect real-world user identity. The competition data does not provide a clean universal user identifier, so the proxy is used to connect transactions that appear to belong to the same behavioral entity.

Missingness is also retained as potentially informative information rather than being treated as meaningless noise.

---

# Historical Transaction Features

A major part of the feature engineering focuses on **historical behavior available before the current transaction**.

Examples include:

* Historical transaction amount statistics
* Cumulative transaction counts
* Transaction frequency
* Deviation from historical transaction behavior
* Transaction velocity
* Email-related features
* Product-related features
* Historical counts
* Other behavioral aggregations

For example, transaction amount behavior can be represented through:

```text
Historical mean transaction amount
                │
                ▼
Current transaction amount
                │
                ▼
Deviation from historical behavior
```

The historical features are constructed so that the current transaction does not use future transactions to describe its own past behavior.

This makes the feature engineering temporal rather than relying on information from transactions that occur later in the sequence.

---

# Vesta Feature Compression

The IEEE-CIS dataset contains more than 300 Vesta-related features with substantial sparsity and missingness.

Instead of feeding all of these sparse features directly into the models, the project groups Vesta features according to their sparsity/missingness patterns.

The resulting blocks are then compressed independently using PCA.

The PCA transformation is configured to retain **95% of the variance** within each block.

```text
Vesta Features
      │
      ▼
Identify Similar Sparsity Patterns
      │
      ▼
Create Feature Blocks
      │
      ▼
PCA per Block
      │
      ▼
Retain 95% Variance
      │
      ▼
Compressed Vesta Features
```

The fitted compressor is saved as:

```text
models/artifacts/v_compressor.joblib
```

The same fitted transformation is reused when constructing the test dataset so that the test data is transformed using the training-derived PCA mappings.

---

# Feature Optimization

Feature optimization is performed after the initial feature construction and Vesta compression.

The optimization process follows:

```text
Raw Features
      │
      ▼
Vesta Block Detection
      │
      ▼
PCA Compression
      │
      ▼
Zero-Gain Feature Removal
      │
      ▼
Correlation Filtering
      │
      ▼
Permutation Testing
      │
      ▼
Final Feature Set
```

### Zero-gain removal

Features providing no measurable gain are removed as an initial pruning step.

### Correlation filtering

Highly redundant features are subsequently filtered to reduce unnecessary duplication.

### Permutation testing

Candidate features are evaluated by shuffling their values and observing the effect on model performance.

The purpose is to determine whether the model is actually relying on the information contained in a feature.

The resulting feature-removal information is stored in:

```text
models/artifacts/optimized_dropped_features.yaml
```

---

# Validation Strategy

Because fraud detection is a temporal problem, the dataset is ordered using:

```text
TransactionDT
```

The feature optimization stage uses an **80/20 chronological split** rather than a random split.

```text
Earlier transactions
        │
        ├──────── 80% ────────► Training
        │
        └──────── 20% ────────► Validation
```

The project also uses **5-fold time-series out-of-fold validation** for model evaluation and ensemble development.

The later folds are particularly important because they are temporally closer to the competition test period.

---

# Model Training

Three gradient-boosting models are trained independently:

* XGBoost
* LightGBM
* CatBoost

The models provide different approaches to learning patterns from the same tabular feature space.

## XGBoost

XGBoost is used as one of the primary high-performing tree-based models for the engineered tabular dataset.

## LightGBM

LightGBM provides a different tree-growing strategy and contributes additional model diversity to the ensemble.

## CatBoost

CatBoost provides another gradient-boosting approach, including native handling of categorical information.

Using three different boosting implementations allows the final prediction to benefit from differences in the models' learned decision boundaries.

---

# Hyperparameter Optimization

Hyperparameters are optimized using **Optuna**.

Approximately 40–50 trials were performed for each model during the tuning process.

The tuning process uses:

* Model-specific search spaces
* Early stopping
* Trial pruning
* Chronological validation
* Out-of-fold evaluation

The resulting parameter configurations are stored as:

```text
models/artifacts/
├── best_xgboost_params.yaml
├── best_lightgbm_params.yaml
└── best_catboost_params.yaml
```

# Ensemble

The final ensemble uses weighted probability averaging.

The optimized weights were:

```text
LightGBM    0.3119
CatBoost    0.2278
XGBoost     0.4603
```

Conceptually:

```text
Final Prediction =
    0.3119 × LightGBM probability
  + 0.2278 × CatBoost probability
  + 0.4603 × XGBoost probability
```

The ensemble configuration is stored in:

```text
models/artifacts/ensemble_weights.yaml
```

Out-of-fold predictions used during ensemble development are also generated for the individual models.

# Limitations

There are several important limitations to the approach.

### Proxy user identity

The `user_id` is an engineered proxy rather than a ground-truth customer identifier. Different real users may potentially be grouped together, while the same real user may potentially appear under different combinations.

### Competition-specific data

The pipeline was developed around the structure and feature availability of the IEEE-CIS dataset. It should not be assumed to transfer directly to another fraud detection dataset without modification.

### Temporal assumptions

The historical feature engineering is designed around the ordering information available in the competition data. A production fraud system would need to account for real-time feature availability, data latency, feature stores, and continuously updated historical state.

### Offline evaluation

The reported leaderboard and validation metrics are specific to this competition and evaluation setup. They should not be interpreted as production fraud-detection performance.
